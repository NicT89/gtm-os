# Examples

Format anchors for the skills. Each file shows the *shape* of an output the skills
describe in prose, so a run has something concrete to match.

| File | Anchors |
|---|---|
| `scan-report.md` | gtm-signal-scan step 7 |
| `audit-log-entry.md` | the audit-log append every skill ends with |
| `blueprint-hiring.md` | gtm-blueprint step 4 output, hiring signal |
| `demo-report.md` | The offline demo's report, generated by `scripts/demo.py`. A test fails if it drifts from the generator's output |
| `demo/fixtures.json` | The demo's synthetic accounts, people and stand-in responses, with each planted hold named |
| `demo/plays.demo.json` | A complete plays file in the shape `check_plays.py` validates. The plays are ILLUSTRATIVE, not anyone's live routing |
| `demo/scoring.demo.json` | A complete scoring config in the shape `score.py` validates. Every value is ILLUSTRATIVE |
| `hubspot/portal-map.example.json` | A portal map for a synthetic HubSpot portal, in the shape `scripts/hubspot_presync.py` reads (references/hubspot-adapter.md) |
| `hubspot/planned-writes.example.json` | Planned writes against that map, in the shape `manage_crm_objects` takes |
| `gtm-mcp/plugin-connector.json` | The GTM MCP connector block, merged into the plugin manifest when GTM MCP launches (references/gtm-mcp.md) |

## These are synthetic

Every company, person, number, and URL in this folder is invented for illustration.
No file here contains real prospect data, and none should ever be edited to add any:
real run artifacts live in the operator's own storage, never in this repo.

They are written to be *structurally* faithful — the right sections, the right level
of specificity, the falsifiability test passing — while being obviously fictional on
inspection. Domains use `.example`, which is reserved and cannot be registered.

When the format changes, update these alongside the skill, or they quietly become
the wrong target.
